# 福清麻将 · 融城茶馆 补花动画与庄家掷骰交互设计稿

- 日期：2026-11-12
- 版本：沿用当前 v1.2.4，本次不升版本号
- 范围：Godot 版（`godot/`）
- 状态：全部问题已确认；两项新交互待实现。金牌显示时机的修复已作为当前 1.2.4 的补丁实现。

## 1. 背景

v1.2.4 已经加入开局发牌、开金、补花的演出和首局掷骰定庄，但两处仍然偏“瞬时完成”：

- 开局补花只显示最终花牌数量，没有逐张展示“摸到花—补花—再摸到花—第二轮补花”的过程；正常摸牌摸到花时也没有任何展示。
- 首局庄家掷骰目前由 `Rules.roll_dealer()` 一次性算完，面板一次性显示四家结果，1.8 秒后自动进入发牌；没有随机起手、逐人按按钮掷骰、骰子投掷动画和平局重掷的过程。

本稿只描述这两项体验改动，不改动牌型、计分、争牌、抢杠规则，也不改版本号。

## 2. 现状实现

### 2.1 开局补花

`Game.deal()` 已经按正确规则做轮次补花：

1. 四家各摸 16 张，庄家补 1 张；
2. 先翻金，再把起手牌里的花牌移到各家花区；
3. `while flower_debts`：按 `order_from(dealer)`（庄家起、行牌顺序）逐家补一张；如果补到的还是花，记入下一轮，直到所有花补完。

问题只在表现层：`OpeningIntro` 的 `flowers` 阶段只更新花牌数量，没有逐张显示补到了什么。

### 2.2 正常摸牌补花

`Game.draw_tile()` 在摸到花时立即把花收入花区，并从牌尾继续摸，直到摸到非花为止（同一家连续补）。这个规则本身符合“摸到花就补”，但目前界面没有“摸到花”的展示和补花动画。

### 2.3 庄家掷骰

- 单机：`begin_game()` 调用 `Rules.roll_dealer()` 一次算完四家点数（含平局重掷），`show_dealer_roll()` 直接显示最终结果，1.8 秒后自动开始发牌。
- 联机：房主进程在 `start` 请求里同样一次算完，把结果写进快照；客户端显示同一结果。
- 没有随机起手、逐人按键、骰子动画和平局重掷的阶段感。

## 3. 补花动画设计

### 3.1 开局补花演出

时间线接在现有 `gold` 阶段之后，替换当前“一帧显示最终花数”的做法：

1. **起手花**：显示各家起手摸到的花，按行牌顺序（庄家起）逐张展示；每张花飞到对应座位的花区。
2. **第 N 轮补花**：按行牌顺序，对每位还有待补花牌的玩家补一张：
   - 补到的不是花：牌进入手牌，界面显示“补牌”即可；
   - 补到的是花：花牌亮出，飞到花区，并记入下一轮；
   - 一轮结束后如果还有花，进入下一轮；直到全部补完。
3. 补花全部结束后，再进入现有的天胡/三金倒/抢金判定。

展示方式（建议）：

- 在牌桌中央或对应座位旁弹出一个小面板，显示座位名、花牌面、「第 N 轮补花」或「摸到花」；每张约 0.3 秒。
- 花牌始终正面显示（花牌本来就是公开信息）；对手的花同样展示，但不需要展示其手牌。
- 不绘制牌墙；补牌来源用“从牌桌下方/牌尾方向滑入”的简化动画表示。
- 全部花牌事件可以点击、空格或回车加速/跳过，沿用现有开局演出的跳过方式。
- 事件较多时（起手花 + 多轮补花），总时长可能超过现有 3–4 秒；建议给补花阶段单独计时，默认每张 0.25–0.3 秒，跳过可立即结束。

### 3.2 正常摸牌遇到花

- 摸牌结果已经是最终状态（花收入花区、补到非花后手牌更新），表现层在 `refresh` 时补一段短演出：
  1. 在摸牌座位旁亮出刚摸到的花；
  2. 显示「补花」，从牌尾方向补一张；
  3. 如果补到的还是花，重复；否则结束，显示最终摸到的牌和可用操作。
- 演出期间隐藏操作按钮、忽略点击，避免在动画中出牌；约每张花 0.3 秒。
- 同一家连续补花按 `第 1 次补花 / 第 2 次补花` 展示，不需要跨家轮次（正常摸牌时只有摸牌者持有待补花牌）。

**关于「是否跨家轮次」的详细说明（已确认：方案 A）**

正常行牌时，只有当前行动的一家在摸牌。比如轮到你摸牌，你摸到一张花：系统显示这张花，你从牌尾补一张；如果补到的又是花，再显示、再补，直到摸到非花为止。这个过程中，其他三家手里没有待补的花牌，所以即便按四家顺序走一轮，其他三家也会直接跳过。

- **方案 A（已采用）**：只展示摸牌者自己的连续补花，第一次、第二次……直到摸到非花。这样和实际操作节奏一致，也不会出现其他三家「无花可补」的空白步骤。
- 方案 B（未采用）：每摸到一次花，都按行牌顺序让四家各走一个补花步骤；其他三家显示「无花」或快速跳过，再回到摸牌者继续。

开局发牌时四家可能同时有花，所以开局一定按四家轮次补；这个问题的范围只是**正常行牌中摸到花**。

### 3.3 数据与接口建议

- `Game` 增加补花事件记录：
  - `deal_flowers: Array`：`{round: int, seat: int, tile: int}`，round 0 为起手花，1..n 为补花轮次；
  - `last_flowers: Array`：最近一次摸牌产生的补花链（`{round: int, seat: int, tile: int}`）；
  - `flower_revision: int`：每次产生补花事件时递增，供 UI 判断是否播放动画。
- `Game.view(seat)` 暴露上述字段；联机快照自动携带。
- 开局演出控制器（`opening_intro.gd`）增加补花子阶段，或在 `table.gd` 用补花队列在 `flowers` 阶段内逐条播放；建议把“事件队列 + 当前事件”放进状态机，便于测试。
- 正常摸牌演出在 `table.gd` 中按 `flower_revision` 变化触发，演出期间 `local_moves()` 返回空。

### 3.5 金牌显示时机（1.2.4 补丁）

当前问题：开局发牌演出还没到掷骰开金，手牌里已经出现金牌高亮/金角标，等于提前泄露了金牌。

规则与表现要求：

- 在 `gold` 阶段之前，渲染层把金牌视为未知：手牌、对手小牌、牌河、副露、金坎、浮动提示都不能出现金牌高亮、金角标或「·金」tooltip。
- 金牌区在 `gold` 阶段之前不绘制；骰子开金动画（`dice` 阶段）结束后，进入 `gold` 阶段才显示金牌区并给手牌加上金标。
- 状态栏、计分等不依赖金牌的信息仍使用真实牌局视图。
- 联机各端使用同一规则，避免某端提前看到金牌。

实现建议：`table.refresh()` 在 `intro_active` 且 `intro.stage` 在 `gold` 之前时，复制一份 `gold = -1` 的渲染视图传给 `render_board` / `draw_seat` / `draw_hand` / `draw_river`；`intro_gold` 为真后使用真实视图。`Rules.is_gold(tile, -1)` 返回 false，因此金标、角标和 tooltip 都会自然关闭。

验收：发牌、庄家补牌、骰子阶段手牌没有任何金牌标记，金牌区不出现；进入 `gold` 阶段后金牌区和手牌金标同时出现。

- 开局补花事件由房主进程生成，随快照下发；各客户端按同一事件顺序播放。
- 正常摸牌的补花事件也在快照中；客户端本地播放短动画。
- 开局演出的宽限（`INTRO_MS`）需要覆盖补花事件的实际时长；如果事件很多，客户端可能落后于服务端，建议服务端在开局阶段给足宽限，或在补花阶段结束后再开放第一阶段。

## 4. 庄家掷骰交互设计

### 4.1 流程

1. 开局后由权威端（单机为本地，联机为房主）随机选一个起手座位。
2. 按行牌顺序轮询四家：
   - 轮到真人：显示「掷骰」按钮，玩家点击后播放骰子投掷动画；
   - 轮到 AI 或其他非本机玩家：短暂停顿后自动掷骰；
   - 骰子动画建议 0.35–0.5 秒：两枚骰子快速跳动，落定后显示点数与和值。
3. 四家掷完后比较和值：
   - 最高点唯一：该玩家坐庄；
   - 最高点并列：并列玩家按当前顺序再各掷一次，重复直到出现唯一最高；
   - 其他玩家保持原点数，不再参与后续重掷。
4. 最终庄家高亮显示，点击「开始发牌」（或短暂停顿后自动）进入现有发牌演出。

### 4.2 界面

- 沿用现有「掷骰定庄」面板，改为四行占位：初始显示座位名，轮到谁才亮出骰子与和值。
- 当前行显示「掷骰」按钮；本机真人可点击，AI 行显示倒计时/省略号后自动完成。
- 平局时插入一行提示「平局，X 与 Y 重掷」，重掷行重新变为待掷状态。
- 面板同时显示当前轮次（首掷/第 N 次重掷），最终庄家行用金色高亮。
- 现有 `Rules.roll_dealer()` 已经实现平局重掷逻辑；建议扩展返回值，记录每一轮的骰子、和值和参与重掷的座位，供 UI 逐轮播放，而不是在 UI 里重新随机。

### 4.3 联机

- 采用**方案 B（真正的掷骰阶段）**：
  1. 房主收到 `start` 后不立即创建牌局，先进入 `rolling` 阶段，并广播掷骰状态：起手座位、当前座位、已掷玩家、骰子点数、和值、轮次、并列者。
  2. 轮到真人时，该客户端显示「掷骰」按钮；点击后向房主提交 `roll` 请求。房主校验当前座位和轮次，用 `_roll_rng` 掷两枚骰子，更新状态并广播。
  3. 轮到 AI 座位时，由房主自动掷（约 0.6 秒延迟）；其他客户端只播放结果。
  4. 四家掷完后，若最高点并列，房主按本轮座次顺序对并列玩家开启下一轮，重复直到唯一最高。
  5. 确定庄家后，房主创建 `Game`、写入 `dealer_rolls`，再进入现有发牌演出。
- 真人超时（建议 8 秒）未提交掷骰时，由房主自动代掷，避免卡住房间。
- 快照新增 `phase: "rolling"` 和 `roll` 状态；客户端在掷骰阶段显示掷骰面板而不是牌桌。
- 按照要求版本号保持 1.2.4；但这是联机协议不兼容改动，旧版本客户端无法加入或会显示异常。正式发布时建议统一升版本。

### 4.4 数据与接口建议

- `Rules.roll_dealer()` 返回值扩展为：
  - `winner`、`dice`、`sums`、`rerolls`（保持现有字段）；
  - `start: int`（随机起手座位）；
  - `history: Array`（每轮：`{dice, sums, rolled, tied}`，`rolled` 为本轮实际掷骰的座位，`tied` 为并列最高者）。
- 单机在 `begin_game()` 用本地 RNG 调用；联机由房主调用并下发。
- `show_dealer_roll()` 改为逐轮、逐座位的状态机：`current_round`、`current_index`、`revealed`、`pending_ties`；按钮回调推进；动画结束回调落定。
- 行为测试：随机起手、逐人推进、平局重掷、最终庄家与 `winner` 一致；UI 测试覆盖面板行状态和按钮。

## 5. 影响面

- `godot/scripts/game.gd`：补花事件记录、`view` 字段。
- `godot/scripts/rules.gd`：`roll_dealer` 的 `start`/`history`。
- `godot/scripts/opening_intro.gd`：补花子阶段（或由 `table.gd` 的队列驱动）。
- `godot/scripts/table.gd`：补花展示、正常摸牌动画、掷骰面板状态机、动画计时、跳过处理。
- `godot/scripts/online_room.gd`：新增 `rolling` 阶段、`roll` 请求、真人超时代掷、掷骰状态广播；`online_table_view.gd`：掷骰状态的座位旋转。
- 测试：`v124_opening_test.gd`/新增补花测试、桌面测试的掷骰与补花交互断言、联机快照字段断言。
- 文档：本稿；实现后的更新说明（本次不升版本，发布时再决定）。

## 6. 已确认与待确认

**已确认**

- **开局补花顺序**：从庄家起按行牌顺序补。
- **正常摸牌补花**：采用方案 A，只展示摸牌者自己的连续补花。
- **动画形式**：座位旁/中央花牌面板，花牌从牌尾方向滑入；每张约 0.3 秒，可跳过；本期不画牌墙。
- **掷骰按键**：单机时 AI 自动掷、本人只按自己的；联机时每个真人轮到自己按，AI 座位由房主自动掷。
- **版本号**：本次保持 1.2.4，不升版本。
- **平局重掷**：沿用本轮座次顺序。
- **联机掷骰**：方案 B——真正的掷骰阶段，逐人提交、房主广播；AI 座位自动掷。

无剩余待确认问题。
